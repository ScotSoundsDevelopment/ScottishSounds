This document serves the team members as a contract, it explains what is expected from each developer in terms of work commitments, sprint participation and communication, as well as what they should expect from the team lead. 
### Project Management
The project is managed using SCRUM, an agile framework that delivers increments working on 2 to 4 weeks sprints. Each Sprint will be planned contextually with the project timeline, only taking onboard a feasible amount of work, and it will contain a series of "ceremonies" (meetings) to check on progress, team dynamics and wellbeing.
Team members are expected to operate as if this is a work space, life happens and it is ok to miss meetings, just be mindful informing the team when this might be the case, practicing respect as one of the main values when interfacing with co-workers.
#### Daily Stand-ups
Stand-ups are scheduled Monday to Thursday at 10am. These are quick meetings, lasting no longer than 15-20 minutes,  in which each developer is allowed to express what they have accomplished the day before, what they will work on for the day, and any blockers encountered. 
If people are not able to attend it is expected to let the team know using the team chat, adding their stand-up asynchronously. 
#### Retrospectives
Retrospectives allow each team member to voice their thoughts on how the team operated during the sprint. It is a great moment for reflecting and addressing what has not worked as planned within team dynamics (Continuous Improvement). We use design thinking to add considerations on a board with 3 main columns: "What went well", "What didn't got well", "What can we improve". Once the board is populated we take the time to review the thoughts that emerged and arrange possible solutions or changes to our work environment setup.
#### Sprint Reviews
This is when we communicated our achievements to Stakeholders. Thursdays will be dedicated at compiling a presentation to report on our increment. Each team member is expected to contribute to the presentation working on the slides that show what they worked on, and present them during the sprint review. If participation is not possible make sure to complete your slides and arrange a script for others to read or a recording to be played on the Friday session.
#### Sprint Planning
In these meetings we plan the work that we take onboard for the coming Sprint. Each developer should take part and give their input on how we rationalise user stories and create tasks for the sprint using design thinking. Team members participation ensure that the right amount of work is selected and that developers can declare the level of availability and amount of work they commit to achieve.
### Developing in a team
Each developer will have the opportunity to write new code as well as review others'.
Developers must engage in Code Reviews (more on Code Reviews can be found in the Code-Practices document) and be comfortable to read and understand other developers' code.
Familiarity with Git version control and working on a hosted repository on GitHub (which will require a dedicated account) is a must, if at any point the version control cloud workflows are unclear please reach out to the team lead, training will be provided.
### Equity and Diversity
It is mandatory that team members treat others with respect and dignity. We should create and maintain an environment where people don't feel discriminated against because of protected characteristic as they are defined in the Equality Act 2010, failing to do so could risk exemption from the project.
